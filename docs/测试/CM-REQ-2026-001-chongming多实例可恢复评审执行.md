# 重明（chongming）评审执行多实例可恢复能力

版本：V0.16
日期：2026-08-17
状态：研发评审稿
目标仓库：chongming（本项目自身）
需求编号：CM-REQ-2026-001

## 一句话描述

将重明需求评审的运行时执行从进程内边界升级为基于 MySQL 的可恢复执行，使评审在单体进程崩溃、多实例重启、模型调用失败等场景下不丢状态、不重放错序，并能把无法自动恢复的失败明确转交人工处置。

## 背景与目标

### 背景

- 当前评审聚合与运行时调度包含进程内边界：默认事件存储、角色激活与调度唤醒均以内存形态为主，服务重启后不能从业务阶段恢复 Harness。
- 与评审相关的 Flyway 迁移（V1 至 V23）和 MyBatis 存储已落地，但领域命令、领域事件与运行态调度仍在同一进程内串行推进。
- README 的“生产化差距”明确把“MySQL 命令写入与多实例恢复”列为发布前必须完成的门槛之一，本项目本次即围绕该差距立项。

### 目标

1. 评审状态与事件可跨进程持久化，重启后可继续推进而非重新开始。
2. 多实例部署时同一 review 在同一时刻只有一名执行者（lease 互斥）。
3. 模型调用、仓库读取等外部失败可重试，达到上限后进入失败转人工，不允许静默假成功。
4. 领域命令与业务事件在同一事务内写入，避免命令成功但事件丢失。

## 需求范围

### 范围内（IN）

- FR-1 至 FR-9 所列持久化、恢复、互斥、失败处理与可观测能力。
- MySQL 5.6 兼容（沿用现有迁移约束：不使用 JSON 列）。
- 向后兼容现有内存实现：未配置持久化时仍可本地演示。

### 范围外（OUT）

- 不重写角色提示词与评审状态机语义（PLAN-003 已定义）。
- 不引入任务队列中间件（如 RabbitMQ/Kafka）；事件推进仍以现有 Dispatcher 模式演进。
- 不做数据库备份/恢复运维脚本的完整落地（仅提供演练脚本）。
- 不改变人工 Gate 决策语义：AI 永远只产出草案，最终由人决定。

## 功能需求

### FR-1 领域命令与领域事件同事务写入

- 描述：任一评审领域命令（启动、提交 Assessment、提交 Claim、辩论回合、Judge、Gate 草案、人工决定）成功后，对应正式业务事件必须与命令写入位于同一数据库事务。
- 验收标准：
  - 模拟事务中途失败时，命令与事件均不可见，不存在半落库。
  - 事件 sequence 在单 review 内全局单调递增，attempt 重试不重置。

### FR-2 事件存储可替换为 MySQL

- 描述：评审事件存储从内存实现可切换到 MyBatis 实现（V1 至 V23 已有表结构），并提供统一接口以保留内存形态。
- 验收标准：
  - 开启持久化后，SSE 历史回放与增量订阅语义与内存实现一致。
  - 重启进程后，事件的 last sequence 与查询接口返回一致。

### FR-3 单 review 执行 lease 互斥

- 描述：多实例共享同一 MySQL 时，每个 review 的运行时调度必须持有数据库 lease；lease 过期或丢失后允许其他实例接管。
- 验收标准：
  - 两个实例同时尝试推进同一 review，只有一个实例进入执行。
  - 持有方进程被杀后，lease 到期自动释放，另一实例可在到期时间后接管。

### FR-4 启动扫描与可恢复 Agent 任务

- 描述：应用启动时扫描数据库中处于执行中/待推进状态的 review，重新驱动对应阶段的 Harness 调度，不以 workspace 文件推断最终业务状态。
- 验收标准：
  - 杀掉进程前记录的业务阶段，重启后从该阶段继续，不重复执行已完成阶段。
  - 扫描具备幂等性，多实例同时启动扫描不产生重复推进。

### FR-5 模型与外部调用失败处理

- 描述：模型网关超时、空流、401/404、仓库读取失败等统一走重试与退避；达到上限后该 review 进入失败转人工状态并记录运行时 Trace。
- 验收标准：
  - 失败达到上限后 review 状态可被查询为人工等待，且原因可追溯。
  - 已部分提交的正式事件不回滚，未提交动作不产生虚假成功。

### FR-6 失败转人工的显式入口

- 描述：系统进入 HUMAN_REQUIRED 的失败分支时，工作台提供明确的“查看失败原因并处置”入口，与正常 Gate 的人工决策分开展示。
- 验收标准：
  - 工作台可从事件流与运行时 Trace 中看到失败链路与重试次数。
  - 人工可对该 review 选择重试、取消或强制以当前状态继续。

### FR-7 运行时 Trace 持久化与回放加深

- 描述：运行时 Trace（工具调用、模型调用元数据、重试、熔断）随事件持久化，重启后仍可回放。
- 验收标准：
  - 重启后 Trace 查询接口返回与崩溃前一致的关键步骤。
  - 敏感内容仍按现有 Redactor 脱敏规则处理，不新增明文密钥暴露。

### FR-8 多实例并发安全

- 描述：lock、事件写入、Gate 草案登记等关键点不因并发请求产生重复或乱序；乐观锁冲突返回明确错误码而非静默覆盖。
- 验收标准：
  - 并发提交同一命令，仅一个成功，其余返回冲突且不产生脏数据。
  - 冲突场景有对应集成测试用例可重复执行。

### FR-9 可观测与运维演练

- 描述：提供故障注入（kill -9、断网、重复事件）与恢复演练的最小脚本，供验收使用。
- 验收标准：
  - 演练脚本能在本地/集成环境跑通，并输出恢复结论。
  - Actuator 或日志能暴露 lease 状态、重试与转人工计数。

## 非功能需求

| 编号 | 维度 | 要求 |
|---|---|---|
| NFR-1 | 可用性 | 单点进程崩溃后，人工介入前系统能自动恢复已受理评审推进（除非进入失败转人工） |
| NFR-2 | 一致性 | 命令与事件同事务；事件回放结果与业务查询一致 |
| NFR-3 | 兼容性 | MySQL 5.6+ 可运行全部新迁移；不使用 JSON 列与窗口函数替代方案 |
| NFR-4 | 性能 | 常规评审规模下（<=8 agents、<=2 辩论轮）开启持久化后的单命令延迟不显著劣于内存实现 |
| NFR-5 | 安全 | 不记录隐藏思维链；Trace 与外发内容按既有脱敏规则处理；多实例共享凭证只经环境变量注入 |

## 现有实现基线（供评审取证）

- 进程内事件默认实现：InMemoryReviewEventStore、InMemoryReviewRegistry。
- 运行时调度：ReviewWorkflowDispatcher（当前仅监听已提交正式事件并在单 review 内串行唤醒）。
- 持久化配置与迁移：ReviewPersistenceConfiguration、db/migration/V1 至 V23。
- 恢复相关既有代码：ReviewRecoveryService、MyBatis 系列 Store、RuntimeTracePersistenceMapper。
- 通知外发：NotificationOutboxWorker（outbox 模式已有表结构与重试字段）。

## 明确不采用的方案

- 不引入独立消息队列中间件承担事件推进。
- 不以 workspace 文件内容推断并覆盖数据库业务状态。
- 不因本次改造修改四个核心角色的推理边界与五态 Assessment/Claim 语义。

## 风险与待辩论点

- 自动重试次数与转人工时机的边界（产品视角希望尽量自动，工程视角倾向保守人工兜底）。
- 事件全量事务化与大事务性能的取舍。
- 多实例 lease 与单体本地演示两种模式并存时的配置复杂度。
- MySQL 5.6 与 8.x 行为差异对锁与迁移的影响范围。

## 验收标准（全流程）

1. 创建评审后，评审可完整走通：受理、计划、四核心角色 Assessment 与 Claim、冲突检测、受限辩论、Judge、Gate 草案、人工决策、报告生成。
2. 在上述流程任意阶段杀进程重启，评审能从持久化阶段继续，事件连续无缺失。
3. 双实例并发推进同一 review 不重复执行。
4. 模型网关返回 500 或超时达上限时，review 进入人工等待且原因可追溯。
5. 提供本次验收的故障注入与恢复演练记录。
