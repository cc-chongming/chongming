# 诊断报告：重启关闭缓慢与内存增长排查

- 仓库：E:\aicode\chongming（Spring Boot 4.0.7 / Java 21 / AIREVIEW 评审平台）
- 诊断方式：静态审计（未改任何 src/main 代码）+ 8081 第二实例动态复现（未触碰 8080/pid 34428）
- 结论概要：**关闭缓慢≈SSE 长连接导致 GracefulShutdown 干等 30s（实测 33s）**；**内存增长≈一批按 review/attempt 只增不减的进程内 Map**，其中 PLAN-060/063 的 liveness/redeliveries 是真实增长源。
- 取证工件：`output/diag-8081-jstack-1.txt`（空闲实例）、`output/diag-8081-jstack-2-sse.txt`（2 条 SSE 连接）、`output/diag-8081-jstack-4-graceful-hang.txt`（优雅关闭挂起约 8s 时抓取）、`output/diag-sse-1.txt`、`output/diag-sse-2.txt`（心跳证明连接存活）、`output/diag-8081-token.txt`。

## 1. 现象与测量数据

### 1.1 启动（同机 8081，-Xmx512m，持久化/模型网关/通知 worker 关闭）
| 指标 | 数值 |
|---|---|
| JVM 启动到 `Started ChongmingApplication` | **3.25–3.30 s**（多次一致） |
| mvnw 全流程（首次含重新编译 305+151 源文件） | 约 1–2 分钟 |
| mvnw 全流程（热编译后） | 约 7–10 s |

空闲堆基线：`jcmd GC.heap_info` → used 57 846 K / 初始 96 256 K / -Xmx512m；一次 register(409)+login(200) 等轻请求后回落至 ~50 MB（有 GC），说明**轻请求本身不放大堆，增长来自按评审积累的结构**。

### 1.2 优雅关闭（关键对比实验）
复现方式：Boot 4 下 `POST /actuator/shutdown`（走 `ShutdownEndpoint → ApplicationContext.close()`，与 SIGTERM 触发的 shutdown hook 是同一套关闭管线）。Windows 下 `taskkill /PID`（不加 /F）对 JVM 控制台进程会被拒绝（“only be terminated forcefully”），故用 actuator 作为可靠、可计时的优雅关闭通道。

| 场景 | 关闭耗时 | 结论 |
|---|---|---|
| **无 SSE 连接**（对照组） | 响应 241 ms，进程退出 **787 ms**（合计 ~1.0 s） | 干净环境关闭非常快 |
| **2 条 SSE 长连接**（`/api/reviews/{uuid}/events`，心跳 15s 保持） | 响应 156 ms，进程退出 **33 048 ms（~33.0 s）** | **SSE 长连接是关闭缓慢的充分条件** |

对照组日志：`Commencing graceful shutdown. Waiting for active requests to complete` → 3ms 后 `Graceful shutdown complete`。
SSE 组日志：
```
16:43:13.920 INFO  [Thread-1] o.s.boot.tomcat.GracefulShutdown : Commencing graceful shutdown. Waiting for active requests to complete
16:43:43.936 INFO  [Thread-1] o.s.c.support.DefaultLifecycleProcessor : Shutdown phase 2147482623 ends with 1 bean still running after timeout of 30000ms: [webServerGracefulShutdown]
16:43:43.966 INFO  [tomcat-shutdown] o.s.boot.tomcat.GracefulShutdown : Graceful shutdown aborted with one or more requests still active
```
即：**关闭阶段恰好干等 spring.lifecycle.timeout-per-shutdown-phase 默认 30s，然后强制 abort**。用户报告的“关闭等很久”与这一数字吻合（30s 级）。

### 1.3 关闭挂起期间的 jstack（约第 8s 抓取，关键栈摘录）
- `"Thread-1"`（触发关闭的线程）：
  `ShutdownEndpoint.performShutdown → AbstractApplicationContext.close/doClose → DefaultLifecycleProcessor.onClose/stopBeans → LifecycleGroup.stop → CountDownLatch.await` —— **卡在等待 webServerGracefulShutdown 这一生命周期阶段完成**。
- `"tomcat-shutdown"`：
  `GracefulShutdown.awaitInactiveOrAborted → Thread.sleep` —— **轮询等待活跃请求数归零**。
- `"container-0"`：`StandardServer.await → Thread.sleep`（服务器保持线程，正常）。
- `"http-nio-8081-exec-*`：`TaskQueue.take`（SSE 异步请求线程早已释放回池，**活跃请求挂在异步上下文中**，Tomcat 判定仍“活跃”）。
- 空闲实例线程全景：非 daemon 只有 `main`、`container-0`、`scheduling-1`（Spring 调度器，context 关闭时会被正常停止）；其余 daemon（`http-nio-*`、`HttpClient-1-SelectorManager`、GC 等）。**没有自建非 daemon 用户线程在空闲态驻留**。

### 1.4 附带发现
- `/actuator/health` 在本地 profile（smtp.sina.com:465）下**挂起 >8s**：spring-boot-starter-mail 的 MailHealthIndicator 在探测时尝试真实的 SMTP 连接（connect 10s/read 30s）。这不是关闭缓慢的原因，但若部署脚本/探活器在重启前调用 health，会叠加延迟。建议 `management.health.mail.enabled=false`。

## 2. 根因排序

### 根因 1（关闭缓慢·实测确证）：SSE 长连接未在关闭时 complete，GracefulShutdown 干等 30s
- `ReviewSseRegistry`（`src/main/java/ai/cc/chongming/review/application/ReviewSseRegistry.java`）：`subscribe()` 用 `new SseEmitter(properties.timeout().toMillis())` 注册后放入 `subscriptionsByReview`，只有 emitter 自身 `onCompletion/onTimeout/onError` 才 remove；**没有任何 @PreDestroy / ContextClosedEvent 钩子把所有 emitter complete()**。
- `ReviewRuntimeTraceRegistry`：`RuntimeTrace.subscribe()` 同样创建 `SseEmitter(30*60_000L)`；其 `@PreDestroy close()` **只 close 两个 virtual-thread executor，未 complete 任何订阅 emitter**（`RuntimeTrace.close()` 虽然会 complete，但只在 `remove(runtimeId)` 中被调用，而 `remove()` 仅 ContextScoutPreviewService 使用）。
- 结果：Tomcat 的活跃请求计数（async context）恒 >0，`GracefulShutdown.awaitInactiveOrAborted` 等满 30s phase 超时才 abort。评审工作台日常开着事件流/AG-UI 流，**每次重启都会中招**。
- 另外 Tomcat 对 async 长连接的等待没有独立于 phase-timeout 的路径可配置，正确的修法就是把 emitter 在关闭时主动 complete。

### 根因 2（内存增长·确定性）：按 attempt/runtime 只增不减的进程内 Map
详见 §4 表。核心几处：
- `ReviewRuntimeTraceRegistry.traces`：**主线 runtime 从不 `remove()`**（只有 preview 会调 `remove`），每次 `resolveTrace` 后当 attempt 永久驻留；持久化开启时 `hydrate()` 会把最多 **20 000 条历史事件**一次性载入内存（`maxEvents=20000`），单 attempt 可达 MB 级。
- `ReviewWorkflowDispatcher.queues`：`onCommitted` 只在 `REVIEW_CANCELLED/REVIEW_FAILED` 时 `queues.remove+tryEmitComplete`；**成功到 COMPLETED 的评审不触发**（事件枚举里没有 REVIEW_COMPLETED），unicast sink + concatMap 订阅永久驻留。
- `ReviewOrchestrationService.plansByRuntime/eventsByRuntime/eventSequences`：只有 computeIfAbsent，**无 remove/forget**。
- `DirectorPlanRevisionPromoter.states`：只有 computeIfAbsent，**无 remove**。
- 终态清理链路缺口：`NotificationOutboxService.markDelivered()` 在评审到 COMPLETED 时只调 `orchestrationService.releaseRuntime()`（→ `AgentScopeReviewRuntimeAdapter.close()`，只清 adapter 自己的 map），**没有清 trace/dispatcher/orchestration/liveness/promoter**。

### 根因 3（内存·次要）：持久化关闭时 In-memory 存储与审计无界
- `persistence.enabled=false` 模式下：`InMemoryReviewEventStore`、`InMemoryReviewRegistry`、`InMemoryReviewAssessmentStore`、`InMemoryReviewDebateStore`、`InMemoryReviewDispatchStore`、`InMemoryHuman*`、`InMemoryReviewReportStore`、`InMemoryContextScoutConclusionStore`、`InMemoryRequirementReviewLaunchCommandStore`、`InMemoryNotificationOutboxStore` 等全部**只增不减**（整库驻留内存）。
- 与持久化开关无关的：`ModelCallAuditService.entries`（CopyOnWriteArrayList，每次模型调用一条，**无界**）、`ReviewIntakeService.submissions`（永不清理）、`AgentScopeReviewRuntimeAdapter.cancelledRuntimeIds`（只 add 不删）、`RequirementReviewLaunchService.HEARTBEAT_EXECUTOR`（static 2 daemon 线程，进程生命周期，不阻塞退出）。

### 根因 4（低概率）：自建非守护线程
- 静态扫到的自建线程只有：`RequirementReviewLaunchService` 心跳池（**daemon=true**，OK）、`RemoteRepositoryMaterializer.drainOutput`（**daemon=true**，OK）、`ReviewRuntimeTraceRegistry` 两个 virtual-thread executor（virtual=daemon，OK）。Reactor `Schedulers.boundedElastic()` 均为 daemon。**未发现会阻塞 JVM 退出的自建非 daemon 线程**。

## 3. 修复建议（仅建议，本次未实施）

### 3.1 关闭缓慢（优先）
1. **`ReviewSseRegistry` 增加 shutdown 收口**
   - 类：`ReviewSseRegistry`
   - 新增 `@PreDestroy void close()`：遍历 `subscriptionsByReview`，对每个 `Subscription.emitter()` 调 `complete()`（try/catch），再清空 map；与现有 `remove()`、`onCompletion` 回调幂等兼容（emitter complete 会触发 onCompletion→remove，需避免 ConcurrentModification，建议先复制列表或先 complete 后 clear）。
2. **`ReviewRuntimeTraceRegistry.close()` 增加订阅收口**
   - 现 `close()`（约 333 行）只 `emitterExecutor.close(); persistExecutor.close()`；
   - 追加：遍历 `traces.values()` 调 `trace.close()`（内部已 complete 所有订阅并清空 events），再 `traces.clear()`；注意与在途 PLAN-068 改造（`StampedEvent.observedAt`、`deliver()` 输出 `createdAt`）合并且不冲突。
3. **显式关闭策略与兜底超时**
   - `application.yml`：`server.shutdown: graceful` + `spring.lifecycle.timeout-per-shutdown-phase: 10s`（显式化、有上限）；即使有遗漏的长连接，最坏也只等 10s。
   - `management.health.mail.enabled: false`（消除 health 探测的 SMTP 挂起）。
4. **验证路径**：复跑 §5 的 8081 复现——开 2 条 SSE 后 `POST /actuator/shutdown`，预期从 33s 降到 <2s。

### 3.2 内存增长
1. **统一的 attempt 终态清理服务（推荐做法）**
   - 新建（示例）`ReviewAttemptCleanupService` / 或在 `NotificationOutboxService.markDelivered`、`ReviewCommandService.cancel/recordStartupFailure`、`failReview` 的同一出口集中调用：
     - `ReviewRuntimeTraceRegistry.remove(runtimeId)`（顺带释放 20k 事件）
     - `ReviewWorkflowDispatcher.completeQueue(runtimeId)`（新增 public 方法：queues.remove + tryEmitComplete + 取消 pending）
     - `ReviewOrchestrationService.forget(runtimeId)`（新增：clear 三张 map）
     - `DirectorPlanRevisionPromoter.clear(runtimeId)`（新增）
     - `ReviewLivenessGuard.clear(key)`（新增，terminal 统一调用）
   - 触发时机：REVIEW_CANCELLED / REVIEW_FAILED 事件已有；补上 COMPLETED（现无 REVIEW_COMPLETED 事件——在 `NotificationOutboxService.markDelivered` 的 transitionTo(COMPLETED) 分支或新增生命周期事件）。
2. **`ReviewLivenessGuard`（PLAN-060/063，见 §6 结论）**
   - `states`：`onCommitted` 中除 CANCELLED/FAILED 外，对 terminal 事件（COMPLETED 落地时的 NOTIFICATION_SENT 等）也 `states.remove(key)`；或在 §3.2.1 清理服务中统一 remove。
   - `redeliveries`：无 evict；建议改为 attempt 作用域并按 attempt 清理，或 LRU/按日清理。
3. **`ReviewWorkflowDispatcher.queues`**：在完成立即 `queues.remove(runtimeId).tryEmitComplete()`，避免累计 sink+订阅。
4. **`ReviewIntakeService.submissions`**：绑定评审终态清理或改为容量受限缓存。
5. **`ModelCallAuditService.entries`**：改成有界环/分页持久化（或用 MyBatis 审计表替代）。
6. **`ReviewRuntimeTraceRegistry.hydrate()`（持久化时）**：空闲 runtime 不必一次性载入 20k 事件，改为按需分页读取或惰性 hydration（仅首次订阅时载入）。
7. In-memory Store 仅影响 `persistence.enabled=false` 的演示/测试模式，正式 MySQL 部署由 MyBatis 仓储替代；如需支持超长会话，给这些 Store 加终态清理或容量上限。

### 3.3 Reactor 订阅
- `ReviewWorkflowDispatcher.queue()` 的 `.concatMap(...).subscribe()` 在没有新事件时不会占用线程（jstack 证实空闲），**不是关闭阻塞源**；但订阅未 dispose，清理队列时应让 sink complete 使订阅自然终止。

## 6. PLAN-060 / PLAN-063 guard maps 是否构成增长源（结论）

- **ReviewLivenessGuard.states（PLAN-060 阶段活性）**：有终态 remove（REVIEW_CANCELLED / REVIEW_FAILED 事件、以及 INITIAL_REVIEW/CONFLICT_DETECTION/JUDGING 的收敛路径），**但是**没有 REVIEW_COMPLETED 事件、成功完成路径不会触发 remove；完成后的 attempt 会在 `states` 永久残留一个 LivenessState（stage 快照 + rewakes 小 map）。➡️ **是增长源（每成功 attempt 数百字节，线性无界）。**
- **ReviewLivenessGuard.redeliveries（PLAN-063 补偿重投）**：**完全没有 remove/evict**，每 commandId 一个 AtomicInteger，随历史派发命令数无界增长。➡️ **是增长源（无界）。**
- **DebateConvergenceGuard.states（PLAN-063 相关看门狗）**：有 remove（noteDirectorWake 超预算收敛前、clear()、scanForStalledDebates 触发后），`clear()` 由 dispatcher 在 CANCELLED/FAILED 时调用；成功完成的辩论不调 clear，但 scan 会按 wall-clock/no-progress（默认 20min/6min）自行移除。➡️ **弱增长源、自愈有延迟（至多 ~20 分钟），建议在 §3.2.1 统一清理里补 clear。**
- 修复口径即 §3.2.2：`states` 对 terminal（含 COMPLETED）统一 remove；`redeliveries` 改为 attempt 作用域并随终态清理，或加容量上限。

## 7. 结论 top3

1. **关闭缓慢**：SSE 长连接未在 shutdown 时 complete（ReviewSseRegistry / ReviewRuntimeTraceRegistry 缺 @PreDestroy 收口）→ Tomcat GracefulShutdown 等满 30s 后 abort（实测 33s）。这是用户所报现象的直接原因。
2. **内存增长（主）**：`ReviewRuntimeTraceRegistry.traces` + `ReviewWorkflowDispatcher.queues` + `ReviewOrchestrationService` 三图 + `DirectorPlanRevisionPromoter.states` + `ReviewLivenessGuard.states/redeliveries` 按 attempt/runtime 只增不减，且成功完成（COMPLETED）路径缺少统一终态清理。
3. **内存增长（次）**：内存模式下 In-memory 各 Store 与 `ModelCallAuditService` 无界；`/actuator/health` 因 MailHealthIndicator 挂起 >8s（部署健康检查会叠加延迟）。
