## 1. 一句话定位

将需求文档与本地代码仓库放入系统，产品、项目、前后端等角色 Agent 基于可验证代码证据完成独立评审、交叉质询和共识裁决，最终输出分角色执行清单与需求 Gate 建议；人工审核决定是否放行，并通过学习通通知 MCP 将结论送达固定责任人。

系统不绑定任何具体业务域或项目管理工具。代码仓库、代码理解能力、通知渠道和模型服务均通过适配器接入，因此可被其他团队直接复用。

### 1.1 与 MT_29 的关系：从协同平台下钻到需求准入决策引擎

本项目源于 MT_29“智能需求分析与研发协同平台”的方向，但不重复建设需求收集、协同编辑、双人审核和历史管理等通用平台能力。我们聚焦其中最影响研发质量、也最容易被 AI 泛化方案做浅的节点：需求进入研发前的可行性评审与准入决策。

MT_29 解决“产品与研发如何在同一平台协同”；本项目解决“一个需求凭什么可以进入研发，以及这个决定如何被证据证明”。未来，MT_29 或任何其他流程平台都可以把本系统作为可插拔的需求 Gate 引擎调用。

### 1.2 核心创新点

1. **角色化上下文对抗，而非多 Prompt 扮演。**所有角色共享同一份需求版本和仓库快照作为事实基线；然后每个角色按职责装配不同代码子集、不同检查清单、不同工具权限和不同输出责任。后端读取服务、接口和数据访问代码，安全读取权限、上传和配置，项目读取交付约束与依赖——它们在同一个代码仓库里看到的是不同维度的证据。这不是给同一段 prompt 换人称，而是为每个角色构造了专属的认知界面。
2. **工具产生、可回跳的代码证据。**代码检索工具返回包含仓库快照、绝对路径、单行号、片段哈希和证据 ID 的 EvidenceBlock；Agent 只能引用已返回的证据 ID，不能凭空声明代码位置。EvidenceValidator 在落库前校验每条证据的路径和哈希——如果评审报告里写着 UserService.java:23，那就是仓库里 UserService.java 的第 23 行，评委可以当场验证。
3. **由真实论点驱动的有限辩论协议。**每一轮运行时先生成结构化 Claim，冲突检测器基于范围、工期、风险等级和证据关系自动识别争议点，随后路由到相关角色进行最多两轮定向质询。固定的是状态机和终止条件（已回应、证据不足转人工、两轮无共识），不是辩论台词。同一需求在同一仓库下运行两次，产生的论点路径可能完全不同。
4. **动态角色路由，不凑数量。**角色由需求语义与初步证据动态激活，Orchestrator 记录激活理由和未激活理由。单次评审最多 8 个 Agent（4 核心 + 3 按需 + 1 Judge），完整角色库的 15 个角色模板按需装配，但从不为了展示数量而拉起无关角色。
5. **人工可控的可执行 Gate + 通知闭环。**Judge 只形成裁决草案和 Gate 建议；人工可确认、退回或 override——所有 override 必须填写理由并追加审计事件。最终结论通过可插拔通知适配器送达固定责任人（首期对接学习通通知 MCP），让 AI 评审的产出真正进入研发协作链路。

本项目最核心的技术资产不是某个模型或角色数量，而是“角色化证据装配 → 真实冲突质询 → 人工可控 Gate”的通用决策协议。这套协议还可迁移到代码审查、技术选型和故障复盘。

## 3. 要解决的问题

需求在产品、项目、研发和测试之间传递时，常会发生范围膨胀、约束遗漏、工期误判和技术风险后移。传统评审依赖临时召集会议，结论往往停留在会议纪要，难以证明“谁依据什么做出了什么决定”。

本系统针对以下结果负责：

- 在开发开始前暴露可被代码与历史上下文佐证的实现风险；
- 让不同立场显式冲突，而不是由一个通用 Agent 给出折中式建议；
- 将评审结论转成责任人、整改项、截止时间和 Gate 状态；
- 保留从需求原文到代码证据、辩论过程、人工审核和通知记录的完整链路。

首期的量化目标不预设“节省两小时”等结论。系统将以同一批标注案例对比单 Agent 与多 Agent 流程的代码证据有效率、已知问题覆盖率、人工采纳率和评审耗时，再用实际结果支撑答辩。

## 4. 首期能力边界

### 4.1 首期必须完成

1. 输入一份需求说明和一个本地仓库目录；Git 仓库可额外记录 branch 或 commit，非 Git 目录也可评审。
2. 只读检索本地代码、配置和接口文档，返回包含文件、单行号、代码片段哈希的证据。
3. 运行固定的四个核心角色，以及最多三个按需角色和一个 Judge。
4. 按“独立评审 → 定向质询 → 裁决建议 → 人工审核”的固定流程收敛。
5. 生成产品、项目、研发等分角色报告，以及统一的 Gate 报告。
6. 人工审核、人工 override 与每次状态变更均留审计记录。
7. 通过学习通通知 MCP 向配置的固定责任人发送最终结论。

### 4.2 首期明确不做

- 不直接连接 Jira、GitLab、禅道或生产发布流水线；
- 不让 AI 自动阻断真实研发流程或自动修改代码；
- 不一次实现十五个角色、复杂记忆系统和所有业务数据源；
- 不把完整仓库无差别发送给模型；
- 不依赖其他团队的代码理解 MCP 才能运行。

## 5. 角色体系：首期最多 8 个 Agent

角色数量分为“完整角色库”和“MVP 单场实例数”两个口径，避免混用：

- 完整角色库：4 个核心角色 + 11 个按需角色模板，共 15 个评审角色；Judge 独立计算。
- MVP 单场实例数：4 个核心角色 + 最多 3 个按需角色 + 1 个 Judge，**每场最多 8 个 Agent**。
- 报告数：按实际激活的评审角色生成，另附 1 份 Gate 总报告；不再固定写成“十一份报告”。

| 类型 | 角色 | 是否首期实现 | 关注点 |
| --- | --- | --- | --- |
| 核心 | 产品 Agent | 必选 | 用户价值、范围、验收标准、平台通用性 |
| 核心 | 项目 Agent | 必选 | 合同/交付约束、排期、依赖与风险 |
| 核心 | 后端 Agent | 必选 | 服务实现、接口、事务、数据一致性与代码改动范围 |
| 核心 | 前端 Agent | 必选 | 页面交互、组件复用、接口契约与可实现性 |
| 按需 | 安全 Agent | 条件激活 | 文件、权限、认证、外部输入、敏感数据 |
| 按需 | 架构 Agent | 条件激活 | 新模块、跨模块调用、通用化设计、技术边界 |
| 按需 | 测试 Agent | 条件激活 | 复杂逻辑、批量处理、异常流、验收和边界 |
| 裁决 | Judge Agent | 必选 | 争议聚类、回应检查、共识草案、Gate 建议 |

按需激活规则由 Orchestrator 根据需求文本和初步上下文触发。例如，批量导入场景会激活安全和测试；“建设通用引擎”会额外激活架构。

### 5.1 角色包实现约束

每个 RolePack 必须同时定义激活规则、专属上下文范围、检查清单和结构化输出，不能只更换一段角色提示词。

完整角色库的 15 个评审角色（4 核心 + 11 按需）均已在下表 5.2 和 5.3 中定义激活条件、专属上下文、结构化输出和实施阶段。Judge 独立计算。首期实现范围为 MVP 标记的角色（4 核心 + 架构/测试/安全按需 + Judge），其余角色保留角色包契约，不进入首期开发排期——但它们在方案中的定义是完整的，第二阶段可直接按契约实现，不需要重新设计。

单次评审先建立共同事实快照：需求版本、仓库路径、可选 branch/commit、代码快照哈希和已检索证据。随后为每个激活角色生成角色上下文包；角色上下文包只包含该角色必要的代码片段、文档片段、检查清单和工具权限。Orchestrator 同时生成角色激活决策，记录“为什么激活、使用了什么条件、为什么未激活其他角色”，供报告和答辩回放。

## 6. 评审流程与人工 Gate

~~~text
需求文档 + 本地仓库路径（可选 branch/commit）
                    ↓
角色识别与代码证据装配
                    ↓
第一轮：各角色独立输出结构化论点
                    ↓
第二轮：围绕争议点定向质询与回应
                    ↓
第三轮：Judge 形成结论和 Gate 建议
                    ↓
人工审核：确认 / 驳回 / Override（必填理由）
                    ↓
最终状态、分角色报告、审计记录、学习通通知
~~~

### 6.1 论点与证据规则

每个角色只能输出结构化论点：

| 字段 | 说明 |
| --- | --- |
| 论点 | 发现的风险、冲突或可执行建议 |
| 角色与等级 | 提出角色，以及 P0、P1、P2 或建议 |
| 证据 | 需求原文位置或经过检索器验证的代码证据 ID |
| 影响 | 影响范围、交付影响或安全影响 |
| 建议动作 | 具体整改项、责任角色和建议截止时间 |
| 回应状态 | 未回应、已回应、已缓解、升级人工审核 |

代码证据由代码上下文工具直接产生，必须包含仓库标识、版本、绝对文件路径、单行号、片段哈希和展示片段。模型输出时只引用已返回的证据 ID；EvidenceValidator 在落库前回跳校验证据 ID 与文件位置。没有有效证据的论点只能标记为“待人工核实”，不能成为阻断理由。

### 6.2 有限辩论协议

- 独立评审：各角色并行提出论点，避免先看到他人结论后随大流。
- 争议聚类：Judge 将相互矛盾或依赖同一事实的论点归为争议点。
- 定向质询：每个争议点最多两轮；被指定角色必须回应、补充证据或承认无法判断。
- 收敛：达到“已回应并有动作”“证据不足转人工”“两轮仍无共识”三种终止条件之一。
- 兜底：超过时间或轮次预算时，系统不继续生成文本，而是进入人工审核。

每次辩论由运行时事件驱动：独立评审产生 Claim，冲突检测器基于 Claim 的范围、方案、工期、严重等级和证据关系形成争议点，随后路由到相关角色回应。系统保存完整 Claim、Challenge、Response 与 Decision 事件序列；Demo 可以固定需求场景和样例仓库，但不得预写辩论台词。

### 6.3 Gate 状态与人工权力

| 状态 | 含义 | 生效者 |
| --- | --- | --- |
| 待评审 | 已提交，尚未启动 Agent 流程 | 系统 |
| AI 建议通过 | 无高风险问题，或仅有非阻断建议 | AI 建议，待人工确认 |
| AI 建议有条件通过 | 存在可跟踪整改项，需指定责任人 | AI 建议，待人工确认 |
| AI 建议阻断 | 存在未解决 P0/P1、关键争议或证据不足的高风险问题 | AI 建议，必须人工审核 |
| 人工通过 / 有条件通过 / 阻断 | 人工审核后的最终状态 | 人工审核人 |
| 已通知 | 最终结果已送达对应责任人 | 系统 |

人工审核人可以确认、退回补充或 override AI 建议。所有 override 必须填写原因；原始论点、证据、模型信息、审核人、审核时间、旧状态与新状态均不可覆盖，只能追加审计事件。

### 7.1 适配器契约

| 扩展点 | 首期实现 | 后续实现 | 复用原则 |

## 8. 模型、数据与安全策略

### 8.1 千问与 DeepSeek

系统通过 ModelGateway 调用千问与 DeepSeek，不把任何模型写死到角色中。首期采用“一个主模型 + 一个可切换模型”的策略：同一角色可按配置选择模型；当主模型超时或不可用时，按策略切换或将评审标记为失败待重试。

每次调用记录模型提供方、模型标识、耗时、请求结果和失败原因，用于复现评审与比较模型效果。密钥仅从环境变量或受控配置读取，绝不写入仓库、提示词或演示视频。

### 8.2 代码与提示安全

- 仅允许只读白名单目录；不执行仓库中的脚本、构建命令或测试命令。
- 检索器先过滤常见密钥文件、构建产物和无关大文件；向模型发送最小必要片段。
- 代码注释、README 和需求附件均可能含有恶意指令，统一作为不可信数据，不能改变系统提示、Gate 规则或工具权限。
- 演示仓库使用可公开展示的本地示例或已获得授权的样例；真实业务仓库需先确认模型服务的数据合规边界。

## 10. 效果验证方案

在第 6 周前建立小型评测集：至少 6 份需求与对应本地示例仓库快照，人工为每份样例标注预期风险和有效证据位置。

| 指标 | 定义 | 对比对象 |
| --- | --- | --- |
| 代码证据有效率 | 证据中的路径、单行号和片段哈希均校验通过的比例 | 单 Agent / 多 Agent |
| 已知问题覆盖率 | 命中的人工标注风险数 ÷ 标注风险总数 | 单 Agent / 多 Agent |
| 人工采纳率 | 人工审核后保留的有效建议 ÷ 全部建议 | 单 Agent / 多 Agent |
| 收敛效率 | 从提交到形成可审核 Gate 建议的耗时和轮次数 | 单 Agent / 多 Agent |

对照实验中使用相同需求、相同仓库快照、同一模型及相同上下文预算。若多 Agent 没有在覆盖率或证据质量上显示优势，答辩中如实说明并调整协议，而不是宣称未经验证的降本数据。

## 13. 主要风险与应对

| 风险 | 应对 |
| --- | --- |
| 多 Agent 无休止辩论 | 两轮上限、统一 Schema、超过预算立即转人工审核 |
| 模型编造代码行 | 证据由检索器生成并校验哈希；无证据论点不能阻断 |
| 外部代码理解 MCP 未完成 | LocalRepositoryAdapter 为默认路径，MCP 只作为增强适配器 |
| AgentScope 相关能力不符合预期 | 将辩论协议状态、结构化事件和 Gate 规则封装在自建 DebateEngine 中；框架只负责 Agent 调用与事件承载，可替换或降级 |
| 千问或 DeepSeek 调用不稳定 | 模型网关配置超时、重试和切换策略；视频准备录制备份 |
| 两人范围过大 | 首期锁定八 Agent 上限与一个主 Demo；扩展功能必须不影响核心闭环 |
| 通知误发或对象错误 | 收件人由配置映射管理；通知只在人工最终状态后触发；发送记录进入审计 |
| 真实代码数据合规 | 默认使用授权样例仓库；真实仓库使用前确认模型服务边界与脱敏策略 |

## 14. 答辩核心表述

我们不是让多个模型自由讨论，而是把需求评审固化成一套可复用的研发决策协议：

1. 用本地代码证据限制 Agent 的判断边界；
2. 用独立评审和定向质询暴露角色冲突；
3. 用确定性 Gate 规则和人工审核保证决策可控；
4. 用适配器把本地仓库、未来的代码理解 MCP 与学习通通知能力解耦；
5. 用完整审计链让每个结论都可以回放、复核和追责。

最终交付的不是一份 AI 总结，而是一条“需求输入 → 证据评审 → 争议收敛 → 人工决策 → 通知执行”的可运行质量门禁链路。

## 16. 方案自评与竞争力分析

### 16.1 团队赛五项维度自评

以下按官方评分标准逐项评估当前方案的设计成熟度和第 6 周 MVP 可争取的分数区间。评分已根据最新评分维度修订。

| 评分维度 | 权重 | 核心考察点 | 方案设计 | 第6周MVP |
| --- | ---: | --- | ---: | ---: |
| 创新性与创意价值 | 30% | 方案新颖度、思路独特性 | 27 | 28 |
| AI工具应用深度 | 25% | AI工具贯穿项目核心环节、协作规范性与效率、Prompt调优解决复杂问题、AI生成内容的审查优化 | 20 | 23 |
| 完成度与交付质量 | 20% | 原型可运行、核心功能完整、边界与异常处理、代码规范与可维护性 | 14 | 17 |
| 技术实现与复杂度 | 15% | 技术选型合理、核心难点攻克、技术前瞻性 | 12 | 13 |
| 答辩与现场表现 | 10% | 创意阐述清晰度、AI协作过程展示、代码级追问应答、现场感染力 | 8 | 9 |
| **合计** | **100%** | | **81** | **90** |

方案设计 81 分的含义：当前文档已将角色激活规则、证据校验机制、辩论终止条件、Gate 状态机和适配器接口定义到可开发的程度——这是"方案写完了"的分数，不是"系统做完了"的分数。第 6 周 MVP 可争取 90 分的前提是主 Demo 真实运行、代码证据可回跳验证、单 Agent 与多 Agent 对照数据可用。

**创新性与创意价值（27→28）**：核心创新不在"多个 AI 聊天"，而在将多 Agent 对话约束为有确定状态机和终止条件的结构化决策协议。与 M_29 通用协同平台互补而不重复，是命题池中"需求准入"空白节点的首次覆盖。答辩时需在 30 秒内展示争议聚类和质询链路以消除"多 Agent 聊天室"的误解。

**AI工具应用深度（20→23）**：此维度考察的是开发过程中使用 AI 的程度，而非产品本身的 AI 能力。两人全流程使用 Codex：从架构设计讨论（辩论协议状态机应设几轮、终止条件如何定义）到代码生成（AgentScope 集成、适配器实现）到测试用例和文档，均经 AI 辅助。关键模块（证据校验规则、角色路由逻辑、Gate 状态机）的 Prompt 链将记录为评审材料。所有 AI 生成代码经双人交叉审查，避免将未审代码直接纳入交付。第 6 周需提交 Codex 协作日志摘录作为此维度的物证；若无过程记录，此维度可能滑落到 15-17 区间。

**完成度与交付质量（14→17）**：两人 6 周交付完整闭环（需求→代码→质询→Gate→人工审核→通知）是可行但紧凑的目标。边界处理（模型超时降级、证据校验失败兜底、通知异常重试）已在设计中预留。6 份评测集和单 Agent 对照实验是交付之外的质量加分项。核心风险是第 5 周仍未跑通最小闭环时未及时砍范围。

**技术实现与复杂度（12→13）**：AgentScope Java 2.0 为底座，核心自研能力是辩论协议引擎、EvidenceBlock 校验链和可插拔适配器。难点不在框架集成，而在工程上让模型的自由文本输出被工具返回的真实证据约束——这需要证据 ID 机制 + EvidenceValidator + Claim Schema 三层配合。技术前瞻性体现在适配器架构使系统可被其他团队直接替换为自己的代码仓库和模型。

**答辩与现场表现（8→9）**：5 分钟视频已规划为六段式结构，配合录屏和本地缓存兜底。每条代码证据可回跳到仓库中对应行号——这是"代码级追问应答"的技术底气。单 Agent 对照数据是区分器：若对照显示多 Agent 覆盖了单 Agent 遗漏的风险点，说服力远超口述。

### 16.2 核心创新点

1. **从"AI 给建议"到"AI 形成可追责的决策依据"。**每个论点以 EvidenceBlock（仓库快照、绝对路径、单行号、哈希）为支撑，事后可复查。

2. **从"单一视角"到"结构性对抗"。**让 4 个核心 Agent 从不同利益立场独立论证、交叉质询，再由 Judge 归并，模拟真实研发中"后端不想改、产品想做大、项目要按时交付"的结构性张力。

3. **从"评审建议"到"流程门禁"。**评审结论是可被状态机驱动的 Gate 建议，配合人工审核和通知闭环。AI 评审从"提效工具"升级为"流程基础设施"。

4. **从"绑定工具链"到"可插拔适配器"。**任何团队接入时只需实现三个接口（ContextProvider、ModelProvider、NotificationAdapter），即可替换为自己的环境。M_29 等协同平台可集成本系统作为需求准入节点。

### 16.3 从 M_29 延伸的差异化定位

M_29 解决的是完整的协同工作流（上传→分析→共创→审核→执行→追溯）。本方案聚焦其中被跳过的决策节点：**需求分析完成后、进入研发执行前——这个需求凭什么可以进入研发？**

- M_29 是一整条协同流水线；
- 本方案是这条流水线上一个可插拔的需求准入 Gate 引擎。

这种"不抢赛道、补空白"的定位降低了与 M_29 的直接竞争，也更容易被评委理解为"有聚焦的深度方案"。

### 16.4 命题池竞争格局（34 个命题分析）

分析全部 34 个命题后，与本案直接竞争的主要集中在以下命题：

| 命题 | 方向 | 重叠领域 | 本方案差异 |
| --- | --- | --- | --- |
| MT_20 | 多Agent协同研发工作流引擎 | 多Agent + 研发协同 | MT_20 是工作流自动化（让 Agent 替代人执行研发任务）；本方案是决策自动化（让 Agent 对抗性评审需求是否该进入研发）。一个是"替你干"，一个是"替你判" |
| MT_15 | AI数字分身平台 | 产品与研发协同 | MT_15 构建角色数字分身辅助日常工作；本方案聚焦需求评审这一特定决策场景，做深而非做宽 |
| MT_42 | AI智能发布风险门禁 | 门禁/Gate 概念 | MT_42 是发布前风险门禁（上线前检查）；本方案是需求准入门禁（开发前检查）。时间节点不同，可互补 |
| MT_10 | AI代码评审与质量检测 | 代码评审 | MT_10 评审已写好的代码；本方案在代码写之前评审需求。前置一个环节 |
| MT_29 | 智能需求分析与研发协同平台 | 需求协同（锚点命题） | 互补关系：MT_29 是协同流水线，本方案是流水线上的需求准入 Gate 引擎 |

34 个命题中约 5-6 个涉及"需求 / 协同 / 门禁"领域。**自主命题赛道的竞争核心来自 MT_20**（同为"多Agent + 研发"方向）。本方案的三条护城河：

- **结构性对抗 vs 流程自动化**：MT_20 让 Agent 替代人执行研发任务，本方案让 Agent 模拟人的立场冲突来检验需求——前者的价值是效率，后者的价值是决策质量；
- **有可量化对照实验**：单 Agent vs 多 Agent 的代码证据有效率和已知问题覆盖率对比，把方案差异从主观感受变为客观数据；
- **有明确技术壁垒**：辩论协议状态机、EvidenceBlock 校验、动态角色路由——不是调一次 API 就能复制的。

核心风险不在创新性而在交付：若第 6 周提交的是一个只能回放预写对话的 Demo，所有差异化叙事都会崩塌。淘汰赛前唯一目标是：在固定需求场景下证明系统运行了真实的代码检索、真实的角色化论证和真实的 Gate 状态迁移。

### 16.5 开发前须确认

1. 千问与 DeepSeek 调用方式与额度是否在比赛期限内稳定可用；
2. 学习通通知 MCP 接口是否可在第 6 周前对接（若不能，准备本地 Mock 降级）；
3. Demo 样例仓库的数据合规性（建议使用开源项目或授权样例，避免真实业务代码的合规风险）；

两人团队决定了首期不能贪多。若第 5 周末仍未跑通"提交需求→代码证据→四核心角色独立评审→人工审核留痕"的最小闭环，立即砍掉按需角色、MCP 扩展和第二 Demo 场景，确保淘汰赛有可运行产物而非只能阅读的文档。
