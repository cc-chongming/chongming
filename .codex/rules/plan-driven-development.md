# 计划驱动开发规则

> 每次功能开发都必须遵循此规则。计划文档与代码分离，但引用关系可追溯。

---

## 核心原则

**先出计划，再写代码，实施中持续更新计划。**

---

## 规则 1：计划先行

开始任何功能开发/重构前，先在对应模块的 `docs/` 目录下创建或更新计划文档。

```
模块根目录/docs/{PROJECT}-PLAN-XXX-功能名称.md
```

**项目名称前缀**: 根据模块确定项目缩写，如 `AGENTOS-PLAN`、`AGENT-PLAN`、`KB-PLAN` 等。

**编号规则**: `PLAN-001`, `PLAN-002`, ... 递增。

**命名规则**: `{PROJECT}-PLAN-XXX-功能简述.md`，中文命名。

---

## 规则 2：计划位置

计划文件写在与代码同级的模块目录下，而非项目根目录。

| 模块 | 计划位置 |
|------|---------|
| ai-service-kb | `ai-service/ai-service-kb/docs/` |
| ai-service-agent | `ai-service/ai-service-agent/docs/` |
| ai-app-agentos | `ai-app/ai-app-agentos/docs/` |
| ai-app-search | `ai-app/ai-app-search/docs/` |
| 跨模块 | `docs/`（项目根目录） |

---

## 规则 3：代码注释标注来源

所有新建或修改的代码文件，必须在类级别或方法级别注释中标注来源计划段。

```java
/**
 * 公共知识库远程 API 客户端
 *
 * [PLAN-001#1.2]
 * @author zyj
 */
```

格式：`[{PROJECT}-PLAN-编号#段号.子段号]`

---

## 规则 4：计划文档结构

每个计划文档必须包含以下部分：

### 4.1 头部元信息

```markdown
> **状态**: ⏳ 待实施 / ⏳ 实施中（步骤 X 已完成） / ✅ 全部完成
> **创建日期**: YYYY-MM-DD
> **目标**: 一句话描述目标
```

### 4.2 背景

简要描述为什么要做这件事，已有基础、约束条件。

### 4.3 分段方案

按编号分段（0, 1, 2, ...），每段包含：
- 目标描述
- 涉及文件（新建/修改分别列出）
- 关键实现细节（SQL、接口、流程图等）

### 4.4 文件清单

分"新建"和"修改"两个表格，每行标注文件路径、计划段、状态。

| 文件 | 计划段 | 状态 |
|------|--------|------|
| `path/to/file.java` | #1.1 | ⏳ / ✅ |

### 4.5 实施顺序

步骤列表及依赖关系：
1. **步骤 0** ✅ → 描述
2. **步骤 1** → 依赖步骤 0
3. ...

### 4.6 风险与应对

已知风险和应对策略。

### 4.7 变更记录

每次更新记录日期和变更内容。

---

## 规则 5：实施中持续更新计划

每完成一个计划段：
1. 更新计划文档对应段的状态标记（`⏳` → `✅`）
2. 在文件清单表中更新该段所有文件的状态
3. 在变更记录添加条目
4. 记录实际与计划的偏差（如有）

---

## 规则 6：计划完成后的收尾

全部段完成后，必须执行以下收尾动作：
1. 将计划状态标记为 `✅ 全部完成`
2. 更新模块 CLAUDE.md 中的目录结构、API 端点、流程图（如有变更）
3. 在 `.learnings/LEARNINGS.md` 中添加本次任务的 learning 条目
4. 更新 `待完成工作` 清单（如有新增待办）

---

## 规则 7：计划的关闭与归档

- **已完成**的计划保持原样，状态标记为 `✅ 全部完成`，作为历史参考
- **已取消**的计划在头部标注 `❌ 已取消（原因）`
- 不删除任何计划文件，保留完整记录

---

## 规则 8：审查依据

Code Review 时以计划文档为准，检查：
- 实现是否覆盖计划所有段
- 代码注释是否标注正确的计划段引用
- 计划状态是否与实际进度一致
- CLAUDE.md 是否已同步更新
